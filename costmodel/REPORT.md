# 推理算力成本：评估流程与实测报告

版本 1.9 ｜ 2026-11-25 ｜ 硬件 RTX 5060 Laptop 8GB + RTX 4090 24GB ｜ 工具 costmodel 0.2 / edgebench 0.1

---

## 0. 一句话结论

在"不缓存答案、每次都自主生成"的约束下，能压的成本只有两件事：**少算**和**少搬**。
本次搭建了一条可复现的评估链路——判据、成本模型、真跑校准——并在两台机器上跑通了：

- **笔记本 8GB（Ollama）**：有效带宽 320 GB/s（标称 448 的 71%），每步固定开销约 1.5 ms，量化兑现 1.45 倍，长上下文把 decode 拖慢 29%，MoE 同体积快 3.6 倍
- **4090 24GB（vLLM / llama.cpp）**：权重侧 801 GB/s（标称 1008 的 79%），batch 1→32 单步只涨 20% 换来 26.7 倍吞吐；
  长上下文每千 token 加 0.19 ms；**fp8 KV 在 Ada 上是净亏 21–26%**；**MoE 专家卸载是断崖，卸载第一层就掉 83%**
- **MoE 的 batch 收益是 18.3×，不是 dense 的 26.7×**；24 GB 卡上 KV 容量实测 50,160 token，它才是真正的天花板
- **功耗几乎不随 batch 变**（283 → 301 W，+6%），所以吞吐提升基本等于能效提升：batch 32 的每 token 能耗是单流的 1/24.6
- **投机解码实测只有 1.05–1.9×**，取决于文本可预测性；vLLM 0.10 已移除草稿模型方式，只能用 ngram / EAGLE / MTP

### 0.1 选型决策矩阵：按场景直接抄

如果只想知道"我这种情况该选什么"，看这张表。完整推导在后面各章。

| 场景 | 首选 | 关键参数 | 别做 | 能拿到多少 | 依据 |
|---|---|---|---|---|---|

1. **先榨 batch，再谈量化，最后才想架构**——batch 不要钱，量化要重训校准，架构要换引擎
2. **容量问题不会因为你换算法消失**：KV 装不下就减 `max-model-len`、减 batch，或者换 KV 更小的模型（MLA）
3. **所有"倍数"都要用你自己机器上的 `calibrate` 校一遍**：本报告的数字锁在下面这套环境上

## 1. 问题与约束

目标：降低大模型推理的算力／能耗成本，但**不允许**用答案缓存、模板复用、语义检索命中这类手段——
每个请求都完整走一遍前向推理，逐 token 自主生成。

**先说清楚这条约束的定位：它是研究基线，不是产品铁律。**

当基线有两个理由：一是它划出了"没有取巧空间的真实成本"，任何优化都得在这个基线上证明自己；
二是它让收益可归因——没有"命中率"这回事，省下来的每一分都来自真的算得少、搬得少。

说它不是铁律，因为它把两件事捆在了一起：**"不锁死输出"是产品质量要求**，
**"每次自主生成"是推导出来的机制要求**。生产环境里该禁的是前者，不是全部。

### 1.1 生产环境该切到哪一层

判据只有一条：**这个答案的失效条件能不能枚举。**

| 层 | 能不能缓存 | 为什么 |
|---|---|---|
| 前缀 KV | 必须 | 语义不变，输出照旧逐 token 生成 |
| 检索 / 工具 / embedding 结果 | 必须 | 缓存的是数据，不是结论 |
| 语义答案缓存 | 有条件 | 只在静态 FAQ + TTL + 文档变更即失效 + 标注来源时 |
| 跨用户答案复用 | 不能 | 上下文不同，概率上必然出错 |

能枚举失效条件的（"这个功能怎么开"），缓存；枚举不出来的（"看看这份合同有什么风险"），不缓存。

一句话：**禁的是复用结论，不是复用计算。**

### 1.2 这个约束决定了优化的性质

- 收益对所有任务一视同仁，没有"命中率"这回事，也就没有"改了反而更贵"的拐点
- 单请求的下降幅度有上限，是渐进式优化，不是断崖式
- 评价标准只有两条：这一次生成里，**算得是不是更少**、**搬得是不是更少**

也正因为如此，本次测到的大头都不需要碰输出语义：batch 26.7×、量化 2.93×、MoE 3.6×。
这条约束卡住的是"取巧"，不是"优化"。

## 2. 第一层判据：方案优化 vs 程序优化

所有手段分两类，分界线只有一条：**要不要换权重文件、改计算图**。

| 类别 | 定义 | 具体手段 | 收益性质 |
|---|---|---|---|
| 方案优化 | 改变"算什么"——权重精度、计算图、解码策略 | 量化、KV 量化、稀疏／动态注意力、投机解码、MoE | 乘法，可叠加 |
| 程序优化 | 不碰权重，只改变"算得有多快"——执行方式 | 算子融合、kernel 调优、显存调度、PD 分离、continuous batching、通信优化 | 除法，天花板由硬件带宽定死 |

两条判断标准：

1. 方案层的收益是乘法（4bit 1.45× 叠投机 1.45× 约等于 ×2），程序层的收益受硬件限制，实测有效带宽到 320 GB/s 就到顶
2. 所以钱要花在方案层的**排序**上；程序层必须做，但别指望它给出量级

## 3. 五条路线的判定

原始判断来自讨论稿，右列是本次实测后的修正。

| 路线 | 类别 | 原始判断 | 实测／修正 |
|---|---|---|---|
| KV 缓存 | 方案 | 性价比最高，只省输入侧的重复计算 | **半对**。省输入是真；但 decode 每步都要重读整个 KV，长上下文时这是持续成本——实测 6,570 序列比 67 序列慢 29% |
| 量化（4bit／8bit／FP8） | 方案 | 按比例温和降功耗，不是机制上减少计算 | **方向对，量级更大**。Q8 比 Q4 多 1.65 倍字节、慢 1.45 倍；扣掉固定开销后就是线性。decode 本来就带宽受限，"按比例"在这里就是全部 |
| 稀疏／动态注意力 | 方案 | 长期有潜力，工程坑深 | **未测**。Ollama 不暴露该开关，需要 vLLM/SGLang 才能验证 |
| 投机解码 | 方案 | 显著降低总运算量 | **未测**，且机制描述要修正：降的是串行步数与权重读取次数，不是 target 的 FLOPs——一次前向喂 k+1 个位置，FLOPs 反而可能上升 |
| 硬件侧调度／显存／通信 | 程序 | 抠边角的收益，必须搭配算法优化 | **方向对，量级不小**。实测每步约 1.5 ms 固定开销（kernel 启动、采样、调度），在 1.7B 上占 5.3 ms 的 28% |

### 被漏掉的一条：MoE

讨论稿没有提 MoE，这是整套结论里省算力最狠的一条。DeepSeek-V3 是 671B 总参、37B 激活，一次前向只碰约 5.5% 的权重，
完全符合"不缓存、每次自主生成"的约束——它不是跳过运算，是让运算只发生在必要的专家上。

本次已实测验证（OLMoE-1B-7B-Instruct，Q4_K_M，6.9B 总参 / 1.3B 激活）：

| 对比 | 文件大小 | 每 token 实读 | ms/token | tok/s |
|---|---|---|---|---|
| OLMoE-1B-7B (MoE) | 4.21 GB | 0.78 GB | 4.10 | 244.0 |
| Qwen3-1.7B (dense) | 1.11 GB | 1.11 GB | 5.30 | 188.8 |
| Qwen3-4B (dense) | 2.50 GB | 2.50 GB | 10.73 | 93.2 |
| dense 7B Q4（按实测斜率推算） | 4.2 GB | 4.2 GB | 14.6 | ~68 |

结论有三条：

1. **激活比兑现了**。文件 4.21 GB，每 token 只读 0.78 GB——就是 1.3B 激活参数在 4.5 bit 下的体积，而不是 6.9B
2. **同体积快 3.6 倍**。和文件一样大（4.2 GB）的 dense 7B 比，244 对 68 tok/s
3. **比小 4 倍的 dense 还快**。和 1.11 GB 的 Qwen3-1.7B 比，文件大 3.8 倍，速度仍快 1.3 倍

成本模型的预测是 254 tok/s，实测 244，误差 4%——说明"每 token 只读激活参数"这个建模假设是对的。

代价在别处：4.2 GB 的权重必须**全部**装进显存（虽然每 token 只读一部分），8 GB 的卡被吃满；
同样是 1.3B 激活，稠密模型只要 0.78 GB 显存。MoE 用显存换带宽。

### 自回归的刚性边界

"N 个 token 至少 N 次前向"在串行依赖上成立，但**前向次数可以摊薄**：MTP 一次前向产出多个 token，投机解码一次前向验证多个候选。
所以真正的下限不是"N 次前向"，而是"N 次前向里，有多少是不得不做的"。

## 4. 成本模型 v0.2

### 4.1 为什么是带宽模型

decode 阶段一次生成一个 token，GPU 里绝大部分时间在**搬权重和 KV**，不在算矩阵。
所以单 token 时间的第一近似是"搬了多少字节 ÷ 每秒能搬多少"，而不是"算了多少次浮点"。

### 4.2 公式

```
bytes/token = 激活参数 × bits/8 + batch × (ctx + k) × 每 token KV 字节
flops       = 2 × 激活参数 × P + 4 × 层数 × P × ctx × hidden      (P = batch × (1+k))
t_step      = max(bytes / BW_eff, flops / FLOPs_eff) + t0
ms/token    = t_step / (batch × (1 + α·k))
```

- `k` 投机解码草稿长度，`α` 草稿接受率
- `t0` 每步固定开销，v0.2 新增
- `BW_eff`、`FLOPs_eff` 是有效系数，必须用实测反解，不能拍脑袋

### 4.3 参数来源

| 参数 | 取值 | 来源 |
|---|---|---|
| 标称带宽 | 448 GB/s | RTX 5060 Laptop 规格 |
| 标称算力 | 60 TFLOPS | 同上（FP16 张量） |
| 有效带宽 | **0.7** | 实测反解，见第 5 节 |
| 每步固定开销 | **1.5 ms** | 实测拟合 |
| 能耗常数 | 20 pJ/byte、1 pJ/flop | 公开的 GPU 量级估计，仅用于相对比较 |

### 4.4 内置模型

| 键 | 层数 / hidden / heads / kv heads / head dim | 参数量 |
|---|---|---|
| qwen3-1.7b | 28 / 2048 / 16 / 8 / 128 | 1.7B dense |
| llama3-70b | 80 / 8192 / 64 / 8 / 128 | 70B dense |
| deepseek-v3 | 61 / 7168 / 128 / 128 / 128 | 671B 总参 / 37B 激活，MLA |

## 5. 实测校准

### 5.1 环境

| 项 | 值 |
|---|---|
| GPU | RTX 5060 Laptop，8 GB，标称带宽 448 GB/s |
| 推理引擎 | Ollama 0.40.16（本体在 C 盘，模型在 `D:\ollama\models`） |
| 模型来源 | ModelScope GGUF 直下 + `ollama create` 导入（绕开 155 KB/s 的官方 registry） |
| 测量口径 | `eval_duration / eval_count`，warmup 后 5 次取中位数 |

### 5.2 数据

| 模型 | 权重 | 序列长度 | ms/token | tok/s | 反解 BW_eff |
|---|---|---|---|---|---|
| Qwen3-1.7B Q4_K_M | 1.11 GB | ~330 | 5.30 | 188.8 | 0.47 |
| Qwen3-1.7B Q8_0 | 1.83 GB | ~300 | 7.67 | 130.3 | 0.53 |
| Qwen3-1.7B Q4_K_M | 1.11 GB | 6,570 | 7.45 | 134.3 | — |
| Qwen3-4B Q4_K_M | 2.50 GB | ~250 | 10.73 | 93.2 | 0.52 |
| OLMoE-1B-7B Q4_K_M (MoE) | 4.21 GB / 实读 0.78 GB | ~400 | 4.10 | 244.0 | 0.67* |

\* MoE 的 `BW_eff` 按每 token 实际读取的 0.78 GB 反解，不是按文件大小；直接拿 4.21 GB 去除会得到 2.3 这种无意义的数。

### 5.3 两个差分，两个独立结论

**差分一：量化。** 同一个模型，Q8 权重比 Q4 多 1.65 倍，时间只多 1.45 倍。
差值就是那 1.5 ms 固定开销——扣掉后两者完全对齐，量化的边际带宽约 304 GB/s。

**差分二：上下文。** 序列从 67 拉到 6,570，多搬 745 MB 的 KV，多花 2.15 ms，边际带宽 343 GB/s。

两条独立路径给出同一个区间：**有效带宽 300–345 GB/s（标称的 67–77%），固定开销 1.5–2 ms**。

### 5.4 拟合结果

```
t ≈ 1.5 ms + bytes / 320 GB/s
```

由此得到两条判断：

1. 小模型慢不是因为带宽差，是因为固定开销摊不开。1.7B 每 token 理论搬运只要 3.5 ms，固定开销占了近三分之一
2. 大模型（70B 以上）固定开销占比趋近于零，`BW_eff` 可以用到 0.75–0.8

按此，模型里跑大模型建议 `--bwEff 0.7 --t0 1.5`。

### 5.5 校准的重要性

写死 0.8 的假设，在 1.7B 上误差 40%，在 70B 上误差 10% 以内。
也就是说：**小模型的绝对数字必须实测，大模型的相对结论可以外推**。

## 6. 4090 实测（vLLM + llama.cpp）

### 6.1 环境

| 项 | 值 |
|---|---|
| GPU | RTX 4090 24 GB，标称带宽 1008 GB/s，PCIe 4.0 x16 |
| 系统 | Ubuntu 22.04，CUDA toolkit 11.8，glibc 2.35 |
| vLLM | 0.10.2（torch 2.8.0+cu128）；transformers 必须钉回 4.55.4 |
| llama.cpp | 源码构建：`-DGGML_CUDA=ON -DGGML_CUDA_NCCL=OFF -DCMAKE_CUDA_ARCHITECTURES=89` |
| 模型 | Qwen3-4B bf16（vLLM）｜ Qwen3-30B-A3B-Instruct-2507 Q4_K_M，17.28 GiB（llama.cpp） |
| 测量口径 | vLLM 用"两个生成长度做差"分离 prefill；llama-bench `-p 64 -n 128 -r 2` |

计时一律不信引擎自报的 tok/s，只信墙钟差值。

### 6.2 batch 曲线：吞吐几乎不要钱

Qwen3-4B bf16，ctx 2048，每请求 128 token：

| batch | step_ms | tok/s | 相对 batch 1 |
|---|---|---|---|
| 1 | 10.14 | 98.6 | 1.00 |
| 4 | 11.00 | 363.5 | 3.69 |
| 8 | 11.14 | 718.1 | 7.28 |
| 16 | 11.52 | 1389.5 | 14.09 |
| 32 | 12.14 | 2635.8 | **26.73** |

- 权重 8.12 GB ÷ 10.14 ms = **801 GB/s**，标称的 79%
- 并发从 1 涨到 32，单步时间只涨 20%——因为一次权重读取被 32 个请求分摊
- 拐点在算力受限才出现；在这个规模上它还没到

**推论**：单请求优化与服务总成本之间差 26 倍。对 dense 模型，这是整套方案里最大的杠杆，比任何 kernel 优化都大一个量级。
但这条不能直接套到 MoE 上——差多少，见 6.7。

### 6.3 长上下文与 KV 量化：反直觉的那一条

同一模型，batch 1，把 prompt 逐步填长：

| prompt tokens | KV 精度 | step_ms | tok/s |
|---|---|---|---|
| ~40 | auto（bf16） | 10.14 | 98.6 |
| 5,190 | auto | 11.19 | 89.4 |
| 10,381 | auto | 12.15 | 82.3 |
| 10,381 | **fp8** | 14.69 / 15.35 | 68.1 / 65.2 |

两条结论：

1. **上下文成本线性可预算**。每 1,000 token 多 0.19 ms，反解边际带宽 **776 GB/s**——和权重侧的 801 一致，
   说明读 KV 和读权重走的是同一条受限通道。KV 读取追平权重需要 ctx ≈ **5.5 万 token**
2. **fp8 KV 在 Ada 上是净亏**。日志明说：

```
Cannot use FlashAttention backend for FP8 KV cache.
Using XFormers backend.
```

   一开 fp8 KV 就丢掉 FlashAttention，慢 21–26%（两次独立复现）。理论上省 0.5 ms 带宽，实际亏 3 ms 的 FA

所以"长上下文才值得开 KV 量化"这句经验在 Ada 上不成立——它**根本不能开**。
要在长上下文省钱，只有两条路：减少 token 数（滑窗、StreamingLLM、H2O），或者换 Hopper（fp8 KV 与 FA 同时支持）。

### 6.4 MoE 专家卸载：断崖，不是斜坡

Qwen3-30B-A3B（30.5B 总参 / 3.3B 激活）Q4_K_M，17.28 GiB，`-ngl 99` 全上 GPU，用 `--n-cpu-moe`（ncmoe）把前 N 层的专家放到 CPU：

| ncmoe（卸载层数 / 48） | decode t/s | prefill t/s | 相对满血 |
|---|---|---|---|
| 0 | **268.9** | 3355 | 1.00 |
| 1 | 46.7 | 1388 | 0.17 |
| 2 | 46.4 | 825 | 0.17 |
| 3 | 38.8 | 585 | 0.14 |
| 4 | 36.5 | 454 | 0.14 |
| 6 | 29.5 | 325 | 0.11 |
| 12 | 22.2 | 205 | 0.08 |
| 18 | 18.2 | 156 | 0.07 |
| 24 | 14.5 | 125 | 0.05 |
| 30 | 12.3 | 105 | 0.05 |
| 36 | 10.5 | 84.8 | 0.04 |
| 42 | 9.4 | 79.7 | 0.03 |
| 48（全部在 CPU） | 8.4 | 74.2 | 0.03 |

全量专家进显存时峰值占用 **17,922 MiB**，24 GB 卡装得下还有 6 GB 余量。

三条判定：

1. **卸载的代价与"卸载多少"几乎无关**。只卸载 1 层，decode 268.9 → 46.7，**掉 83%**；之后 1→48 层才再掉到 8.4。
   机制：只要有一层专家在主机侧，每个 token 就要为它做一次 host→device 同步；batch=1 时 CPU 侧的专家矩阵乘完全是延迟受限的
2. **prefill 跌得更早更陡**。1 层就 -59%（3355→1388），因为 prefill 是 CPU 上真的在做矩阵乘
3. **全在 CPU 仍有 8.4 t/s**，这是 MoE 的结构优势：每 token 只算 3.3B 激活。换成 30B dense 早就 1 t/s 级别

**对方案的影响**：单卡上的"MoE 专家缓存／按热度换入换出"不存在渐进收益——
它实际是"要么全进显存，要么吞吐变成十分之一"。16 GB 卡跑这个模型要卸载约 6 层，得到 29.5 t/s，是 4090 的 1/9。
这种情况该换更小的 MoE（OLMoE 在 8 GB 上都够用）或买更大的卡，而不是写卸载调度。

补充（见 6.7）：直接挂 hook 测出来，batch 32 时每层专家并集只覆盖 **42.9%**，远低于均匀路由下的 87.3%。
这不改变逐层卸载的结论（那是每 token 一次主机传输），但说明"热专家常驻显存、冷专家冷备"在原理上有依据。

### 6.5 两台机器合起来看

| 观测 | 笔记本 8 GB（Ollama） | 4090 24 GB（vLLM / llama.cpp） |
|---|---|---|
| 有效带宽 | 320 GB/s（标称 71%） | 801 GB/s 权重侧、776 GB/s KV 侧（79%） |
| 固定开销 | 约 1.5 ms／步，在 1.7B 上占 28% | 未单独拆（vLLM 走 CUDA Graph + 连续批处理） |
| 量化兑现 | Q4 vs Q8：字节 1.65×、时间 1.45× | KV fp8：反而 -21~26% |
| 长上下文 | 6.5k 序列慢 29% | 每千 token +0.19 ms，线性 |
| 批处理 | 未测（Ollama 不开） | 1→32：+20% 时间、26.7× 吞吐 |

一句话：带宽模型在两种硬件上都成立（71% 与 79%），但"为什么慢"的解释权在引擎手里——
Ollama 那 1.5 ms 的每步开销，在 4090 上被批处理和 CUDA Graph 抹掉了。

### 6.6 对《本地推理系统优化方案》的直接结论

| 方案里的模块 | 实测结论 |
|---|---|
| 模块 4 MoE 专家缓存 | ❌ 单卡不成立，断崖（1 层 -83%） |
| 长上下文 KV 量化 | ❌ Ada 上净亏，不能用 |
| 调度／固定开销 | ⚠️ 笔记本上占 28%，但那主要是 Ollama 的 Go/HTTP 层；换 vLLM 后这一项消失 |
| 成本底座 | ✅ 已在跑，两层硬件都验证过 |
| 精度回归、perplexity + 任务集 | ✅ 仍必要，但只是准入不是收益 |
| 写引擎／改 kernel | ❌ 在 26.7× 的 batch 杠杆面前量级不对 |

还有一个方法论要求：**测 15% 的收益必须上服务器**。笔记本噪声 20–40%，4090 上重复测量波动 ±0.5%，差两个数量级。

### 6.7 MoE 能不能吃 batch 红利：一次预测失败

6.2 的 26.7× 是 dense 4B 测的。把这条直接套到 MoE 上是错的，但错多少得实测。

Qwen3-30B-A3B GPTQ-Int4（16.9 GB），vLLM 0.10.2，`max-len` 4096，每请求输出 128 token：

| batch | step_ms | tok/s | 相对 b=1 | 按"均匀路由 + 专家并集"预测 |
|---|---|---|---|---|
| 1 | 7.39 | 135.2 | 1.0× | 1.0× |
| 4 | 8.29 | 482.3 | 3.6× | 2.2× |
| 8 | 8.68 | 922.1 | 6.8× | 3.0× |
| 16 | 9.67 | 1654.9 | 12.2× | 4.1× |
| 32 | 12.93 | **2474.1** | **18.3×** | 6.2× |

实测 18.3×，比 dense 的 26.7× 低 31%，但不是腰斩。

**预测错在哪。** 原先的推算是：128 个专家、top-8，batch=b 时并集占比 `1-(1-8/128)^b`，
batch 32 时 87.3% 的专家权重都要被读到，MoE 的省带宽优势基本消失。

这一条后来做了**直接测量**，不再是反推。做法是给 `FusedMoE.select_experts` 挂 hook，
记录每个 decode step 每层真正被选中的专家 id（Qwen3-30B-A3B GPTQ-Int4，48 层 × 128 专家 × top-8，64 输出 token）：

| batch | 每层并集专家数 | 并集占比 | 均匀路由预测 | 前 1/8 专家吃掉的份额 | 均匀时该份额 |
|---|---|---|---|---|---|
| 1 | 8.0 | 6.25% | 6.25% | 21.1% | 12.5% |
| 8 | 44.0 | 34.4% | 40.3% | 17.9% | 12.5% |
| 32 | 54.9 | **42.9%** | 87.3% | 17.6% | 12.5% |

- batch 1 的并集恰好等于 8，正好是 top-8 本身，说明 hook 抓的是真路由
- 并集增长远慢于均匀假设：b=32 时按均匀该有 111 个专家被碰到，实测只有 55
- 前 1/8 的专家拿走了 17.6–21.1% 的选择，是均匀值的 1.4–1.7 倍——**偏斜真实存在，但没有传说中那么极端**
- 从时间反解时我估的是 36%，实测 42.9%，方向对、数值偏低 7 个点；6.7 的结论不因此改变，但数字以实测为准

于是 batch 32 每步读的专家权重是 15 GB × 0.429 ≈ 6.4 GB，加上 2.5 GB 非专家参数约 8.9 GB，和反解的"约 8 GB"对得上。

这也是为什么小 batch 时 MoE 看起来"省得更多"：它省的不只是激活比例，还有冷专家根本不被碰。

> 数据：`edgebench/runs-4090/router-gptq.json`，脚本 `edgebench/router_probe.py`。
> 注意该次测量被迫跑 `enforce_eager=True`（CUDA graph 捕获期间不能读回首 token 的 topk 张量），
> 所以那一轮的 tok/s（27.3 / 203.2 / 797.6）**不可**与 6.7 表里的数字横比，只有并集统计有效。

### 6.8 真正折断杠杆的是 KV 容量

vLLM 加载该模型后给出的原话：

```
GPU KV cache size: 50,160 tokens
```

30B-A3B 的 KV 只有 96 KiB/token（48 层、4 个 KV 头、head_dim 128，bf16），比 Qwen3-4B 的 141 KiB 还小 32%——
GQA 压得狠，所以 4 万多 token 装得下。但它仍然是有限的：

| 并发 | 每请求可分配上下文 |
|---|---|
| 1 | 50,160 token |
| 8 | 6,270 token |
| 32 | **1,567 token** |

所以正确的说法是：**显存余量限制的是「batch × 上下文」的乘积，不是 batch 本身**。
24 GB 卡跑 30B-A3B，你要么吃高并发（32 × 1.5k），要么吃长上下文（1 × 5 万），不能同时要。

把这条压到墙上看一眼——固定 8k 上下文（实测每次 5,190 token），扫 batch：

| batch | 总 token 需求 | step_ms | tok/s |
|---|---|---|---|
| 1 | 5,190 | 7.92 | 126.2 |
| 4 | 20,760 | 10.22 | 391.2 |
| 8 | 41,520 | 13.11 | **610.4（峰值）** |
| 16 | 83,040 | 30.44 | **525.6（崩塌）** |

batch 8 是能整批塞进 50,160 的最后一档（41.5k）。batch 16 要 83k，超了 65%，调度器只能分批放行，
step 时间翻三倍，吞吐反而比 batch 8 低 14%。

这就是"KV 是天花板"的实测形态：**不是 OOM，是排队**。超容量之后不会报错，只会悄悄变慢——
所以线上观察到的"batch 加不上去"，往往是 KV 容量而不是算力。

### 6.9 引擎选型被 batch 支配

同一个模型（GGUF Q4 vs GPTQ Int4，量化格式不同，但可作量级参考）：

| 引擎 | batch 1 | batch 32 |
|---|---|---|
| llama.cpp（GGUF Q4_K_M） | **268.9 t/s** | 未测 |
| vLLM（GPTQ-Int4） | 135.2 t/s | **2474.1 t/s** |

低并发时 llama.cpp 快一倍（GPTQ 反量化 + vLLM 调度开销），高并发时 vLLM 反超。
**没有"更快的引擎"，只有"某个 batch 区间更快的引擎"。**

### 6.10 路线 3 的反转：KV 量化在 llama.cpp 里是划算的

同一 30B-A3B，8k 上下文深度（`-d 8192`，此时 KV 读取已经占相当比重）：

| KV 精度 | decode t/s | 相对 f16 |
|---|---|---|
| f16 | 208.7 | — |
| q8_0 | 190.2 | **-8.9%** |

在 llama.cpp 里把 KV 压到 q8 只付 9% 速度，换来 KV 减半——在显存受限时这是纯赚。
而 vLLM 的 fp8 KV 是 -21~26%，因为它一开就丢掉 FlashAttention。
**差别不在硬件，在引擎**：所以"Ada 上不能做 KV 量化"这个结论要改成"vLLM 在 Ada 上不能做"。

### 6.11 功耗：快是不是等于省电

用 `nvidia-smi` 每 100 ms 采一次 `power.draw`，与 Qwen3-4B 的 batch 曲线同步（温度/功耗墙没锁，空载 22.1 W）：

| batch | tok/s | 实测功耗 | 每 token 能耗 | 相对 b=1 |
|---|---|---|---|---|
| 1 | 92.0 | 283.1 W | 3,077 mJ | 1.00× |
| 4 | 341.7 | 253.7 W | 742 mJ | 4.14× |
| 8 | 675.1 | 262.2 W | 388 mJ | 7.92× |
| 16 | 1,307.8 | 274.4 W | 210 mJ | 14.66× |
| 32 | 2,405.3 | 301.1 W | **125 mJ** | **24.57×** |

三件事：

1. **功耗几乎不跟 batch 走**。283 W → 301 W，只涨 6%，而吞吐涨了 26 倍。原因很直白：batch 1 时卡已经在接近满载的功耗状态下工作，
   只是 SM 在等显存（memory-bound），时钟拉满、算力空转。**低 batch 不是省电，是白烧电。**
2. **能效倍数 ≈ 吞吐倍数**（24.57× vs 26.7×，差的那 8% 就是那 6% 的额外功耗）。所以在单机多流场景里，"省电"和"提吞吐"是同一件事。
3. **电费不是成本**。单流 3,077 mJ/token，一次 128 token 的回答约 394 J ≈ 0.00011 kWh，按 0.6 元/度算约 0.00007 元。
   真正的成本是卡时（这台机器 2.3 元/小时），是电费的几千倍。

这也是为什么大厂拼的是"每卡每秒多少 token"，而不是"每 token 多少瓦"。

### 6.12 投机解码：收益完全由文本可预测性决定

先一个坏消息：**vLLM 0.10.2 已经不支持草稿模型式的投机解码**，原话是

```
NotImplementedError: Speculative decoding with draft model is not supported yet.
Please consider using other speculative decoding methods such as ngram, medusa, eagle, or deepseek_mtp.
```

所以本机没测成"小模型猜、大模型验"的经典形态（llama.cpp 里还要另编 `llama-cli` 才有）。改用 vLLM 的 **ngram**（prompt lookup）投机，
它对"输出里重复 prompt 已有片段"的任务有效，正好可以量出投机解码的收益边界（Qwen3-4B，`num_speculative_tokens=5`，128 token 输出）：

| 任务 | batch | 基线 tok/s | +ngram tok/s | 倍数 |
|---|---|---|---|---|
| 自由生成（解释带宽） | 1 | 92.4 | 99.0 | 1.07× |
| 自由生成 | 4 | 341.7 | 362.3 | 1.06× |
| 自由生成 | 8 | 677.7 | 711.7 | 1.05× |
| 复述给定段落 | 1 | 93.7 | 142.3 | **1.52×** |
| 复述给定段落 | 4 | 345.7 | 525.0 | **1.52×** |
| 复述给定段落 | 8 | 683.2 | 1,308.7 | **1.92×** |

结论：

- **投机解码不是白拿，是赌文本可预测**。自由推理只有 5–7%，复述型任务 1.5–1.9×
- 成本模型里算的 2.80×（α=0.6、k=3）是**乐观上限**，对应"猜中率 60%"的理想情形；实测自由生成对应 α 大约只有 10–15%
- 真实业务大多落在中间：代码补全、JSON 输出、模板化回复这类"半重复"文本才是它的主场
- 大 batch 下收益反而更大（1.92× > 1.52×），因为它省的是串行步数，而 batch 大了之后瓶颈正是步数

### 6.13 量化到底伤了多少精度：PPL 涨 12.6%，题一道没多错

前面所有实验都假设"INT4 基本无损"，这一条之前**一次都没测过**。补上的方式是同一引擎、同一份语料、只换权重：

Qwen3-4B base，vLLM 0.10.2，比较 bf16 与 AWQ-Int4（W4A16）；语料 wikitext-2 raw test，32 个 chunk × 1024 token = 32,736 token：

| 模型 | PPL | 相对 | 多选题准确率 | 平均 margin |
|---|---|---|---|---|
| Qwen3-4B bf16 | **15.17** | 1.000 | 28/32 = 87.5% | 3.296 |
| Qwen3-4B AWQ-Int4 | **17.08** | **1.126** | 27/32 = 84.4% | 3.141 |

先做方法校验：用 transformers 直接前向算同样两个 chunk，得到 9.6952 / 20.1363，vLLM 的 `prompt_logprobs` 给出 9.6682 / 20.0834，差 0.3%。**PPL 的数字可信。**

| 题型 | bf16 | AWQ-Int4 |
|---|---|---|
| 算术（12 题） | 12/12 | 12/12 |
| 中文常识（8 题） | 7/8 | 7/8 |
| 代码输出（6 题） | 6/6 | 6/6 |
| 逻辑（6 题） | 3/6 | 2/6 |

**两个数字指向相反的结论，而且同时成立：**

- 语言建模层面，量化确实漏了气：PPL 涨 12.6%，这是分布上每处概率都轻微偏移的累积
- 任务层面只有 1 道题翻转，落在逻辑题上；算术和代码一道没错

所以"精度压太低会悄悄损伤能力"这句判断，**方向对、机制要改**：损伤不是让模型答错，而是让它对正确答案的信心变弱。
多选题这种只看 argmax 的指标对这类损伤几乎不敏感——**拿任务准确率做精度准入门槛，会漏掉真实退化**。

**对方案的影响（模块 6 精度回归）**：准入指标必须包含 PPL 或 KL，任务集只负责兜住"翻车"，不负责测损伤。
另外 32 条题里差 1 条就是 3.1 个百分点，**这个差在噪声里**，不要当结论。

> 数据：`edgebench/runs-4090/ppl-4b-bf16.json`、`ppl-4b-awq.json`、`mc-4b-bf16.json`、`mc-4b-awq.json`。
> 脚本：`edgebench/ppl_probe.py`（PPL）、`edgebench/mc_probe.py`（多选打分）、`edgebench/ppl_check.py`（交叉校验）。
> base 模型不跟指令，所以最早那版"直接问、对答案"的探针只有 17.6% 正确率——那不是精度问题，是问法问题。

## 7. prefill：同一张卡上的另一种病

### 7.1 decode 的结论不能套过来

decode 是带宽受限：每步把权重读一遍，算力闲着。prefill 反过来——权重只读一遍摊到 P 个 token 上，
但每个 token 都要过全部线性层，瓶颈变成算力。同一张卡，两种模式下"效率"的定义完全不同。

所以"batch 是最大杠杆"这句话只对 decode 成立。prefill 的杠杆是**少读字**，不是多并发。

### 7.2 实测（5060 笔记本，Ollama，固定 num_ctx=16384）

| 模型 | 权重 | ~130 tok | ~465 tok | ~915 tok | ~1810 tok | ~3605 tok | ~7200 tok |
|---|---|---|---|---|---|---|---|
| Qwen3-1.7B Q4 | 1.11 GB | 6,263 | 8,402 | 8,684 | **9,458** | 8,925 | 8,124 |
| Qwen3-4B Q4 | 2.50 GB | 3,195 | 3,814 | 3,732 | **3,958** | 3,745 | — |
| OLMoE-1B-7B Q4（1.3B 激活） | 4.21 GB | 4,093 | 7,497 | **8,285** | 7,921 | 7,448 | — |

单位 tok/s。反解有效算力：

| 模型 | 平台吞吐 | 每 token 计算 | 有效算力 | 占标称（60 TFLOPS） |
|---|---|---|---|---|
| Qwen3-1.7B | 9,450 tok/s | 3.4 GFLOP | 36 TFLOPS | 60% |
| Qwen3-4B | 3,960 tok/s | 8.0 GFLOP | 34 TFLOPS | 57% |
| OLMoE（MoE） | 8,290 tok/s | 2.6 GFLOP | 22.5 TFLOPS | 37% |

**MoE 的 prefill 比 dense 更亏**：每个 token 命中的专家不同，GEMM 又小又碎，效率只有 dense 的 2/3。
这和 6.7 的结论互为补充——decode 时 MoE 靠"少读权重"占便宜，prefill 时 MoE 靠"少算"占不到便宜，反而被碎片化拖累。

短 prompt 还有一笔固定开销：130 token 时 1.7B 只有 6,263 tok/s，比平台值低 34%。扣掉计算时间，固定开销约 **8–15 ms/次**
（权重要先读一遍、图要建一次），比 decode 的 1.5 ms/step 大一个量级。

**这些数字是冷却后的首次测量。** 如果是背靠背连跑（扫 6 个长度、每点 3 次），同一台机器会低 10–15%：
prefill 把算力打满，笔记本的功耗墙比 decode 来得更快。所以"平台吞吐 9,450"和"8,100"都对，
前者是冷机、后者是连续测量；引用时按 ±10% 理解，不要当常数。

### 7.3 模型

```
bytes  = max(激活, 总参数) × bits/8        # MoE 长 prompt 下专家并集趋近全部
flops  = 2 × 激活 × P + 4 × 层数 × P² × hidden
t      = max(bytes/带宽, flops/有效算力) + 固定开销
```

用 5060 校准：dense `有效算力 = 0.60 × 标称`，MoE 再打 0.65 折，固定开销 6 ms。三模型预测误差：

| 模型 | 实测 | 模型 | 误差 |
|---|---|---|---|
| Qwen3-1.7B @1810 | 9,458 | 9,150 | -3.3% |
| Qwen3-4B @1811 | 3,958 | 4,097 | +3.5% |
| OLMoE @1817 | 7,921 | 8,026 | +1.3% |

（`costmodel --prompt <n>` 就能算这一段）

### 7.4 长 prompt 什么时候开始变贵

注意力是 O(P²)，线性项是 O(P)。两者的交叉点：

| 模型 | 交叉点 |
|---|---|
| Qwen3-1.7B | ≈ 14,800 token |
| Qwen3-4B | ≈ 21,700 token |

交叉点之前，"长上下文"只影响 decode（KV 读取）和显存容量；交叉点之后，prefill 本身开始被注意力吃掉。
实测佐证：1.7B 从 1,810 拉到 7,192 token，吞吐从 9,458 掉到 8,124（-14%），此时注意力占计算量约 21%——
和模型预测的降幅一致。
这也解释了 6.8 里那个观察：8k 上下文时 prefill 还没被注意力拖累，掉吞吐的是 KV 容量而不是算力。

### 7.5 对方案的结论

- **PD 分离的真正理由**：prefill 算力受限、decode 带宽受限，混在一张卡上两边都吃不饱。这是结构性的，不是调参能解决的
- **chunked prefill 是有代价的**：把长 prompt 切块塞进 decode 的空隙，会拉高 decode 的 step 时间（互相干扰），要按"每块多少 ms"给预算，而不是"能塞就塞"
- **长 prompt 的成本被低估**：32k 上下文在 1.7B 上光 prefill 就要约 4 秒（按 8,100 tok/s），比很多人以为的"毫秒级"高两个数量级
- **投机解码对 prefill 无效**：它省的是 decode 的串行步数，prefill 本来就是并行的

| 文件 | 用途 |
|---|---|
| `costmodel/costmodel.mjs` | 单步 decode 成本模型，跑对比表、找 batch 拐点、算 KV 拐点 |


## 9. 局限

- **prefill 的模型只在单卡单机上拟合**：5060 上 dense 57–60%、MoE 37%，换卡要重新标定
- **prefill 只测到 7.2k token**：更长的 prompt（32k+）没有实测，交叉点之后的曲线是外推
- **无 PD 分离**：prefill 与 decode 抢同一张卡的成本没算
- **无通信**：多卡 EP/TP 的 all-to-all 开销不在内
- **固定开销按常数处理**：真机上它随 batch、序列长度变化
- **MoE 搬运模型不建模路由偏斜**：6.7 直测到 batch 32 并集仅 42.9%（均匀假设 87.3%）；成本模型按均匀口算，因此低估 MoE 的 batch 收益
- **KV 容量只测了一种配置**：50,160 token 来自 gpu_util 0.92 + max-len 4096 的组合，换参数会变
- **vLLM 与 llama.cpp 的数字不可横比**：量化格式（GPTQ vs GGUF）、调度器、反量化路径都不同
- **测量噪声 20–40%**：笔记本功耗墙和温度，小数点后第二位不可信
- **稀疏注意力未实测**：vLLM／Ollama 都不直接暴露这个开关，需要 SGLang 或改 attention backend
- **投机解码只测了 ngram 形态**：vLLM 0.10 不支持草稿模型，EAGLE／MTP 要另配权重，没跑
- **功耗只有单卡单模型数据**：4090 + 4B，未锁频，笔记本/多卡不适用
- **量化精度只在一个点测过**：4B 的 W4A16、32 条题、一份英文语料（见 6.13）；更大模型和 KV 量化下的精度没测
- **4090 数据是单卡、两套引擎口径不同**：vLLM 与 llama.cpp 的 tok/s 不能直接横比
- **MoE 卸载曲线只测了 batch=1**：有批处理时 CPU 专家能摊薄，实测数字会更乐观（这也是 llama.cpp 服务模式的真实情况）
- **没有 NVLink／多卡数据**：EP/TP 的 all-to-all 成本未覆盖

## 附录 A：本次踩过的坑

> 所有坑都与版本绑定：vLLM 0.10.2、transformers 4.55.4、torch 2.8.0+cu128、Python 3.10。
> 换版本后这些坑可能消失，也可能换一副面孔。

1. **GitHub 直连被阻断**，镜像按 IP 限速（4 连 378 KB/s，8 连反而 176 KB/s），并行无效
2. **镜像会在数据流里塞 nginx 错误页**（本次塞了 3 处共 178 字节），必须逐片校验 HTTP 206 与字节数，再对整包做 SHA256
3. **NSIS 安装器忽略 `/D=`**，Ollama 本体被装进 C 盘用户目录（3.2 GB，主要是两套 CUDA runner）；`Start-Process -Wait` 会因子进程常驻而永不返回
4. **官方 registry 只有 155 KB/s**，改用 ModelScope GGUF + `ollama create` 导入，5.6 MB/s
5. **首次测量偏差 40%**：同一模型同条件，第一轮测出 125 tok/s，重测是 188 tok/s。教训是必须 warmup + 多次取中位数
6. **transformers 5.x 与 vLLM 0.10.2 不兼容**：`Qwen2Tokenizer has no attribute all_special_tokens_extended`，钉回 4.55.4 才好
7. **doctor 误报 FAIL**：torch 2.8.0+cu128 的 `get_arch_list()` 里没有 `sm_89`，但 4090 靠 PTX JIT 照跑。改成真跑一次 64×64 matmul 判断
8. **实例可能是"无卡模式"启动**：`NVIDIA_CPU_ONLY=1`、`/dev/nvidia*` 不存在，要先关机再按 GPU 模式开机
9. **llama.cpp 官方预编译包要 glibc 2.38**：Ubuntu 22.04 是 2.35，报 `GLIBCXX_3.4.32 not found`，只能用源码构建
10. **新版 llama.cpp 要 CUDA 12**：PDL 的 `cudaGridDependencySynchronize`、NCCL 的 `ncclConfig.maxCTAs`。
    CUDA 11.8 下必须 `-DGGML_CUDA_NCCL=OFF` 且只编 `CMAKE_CUDA_ARCHITECTURES=89`
11. **Ollama 会缓存 prompt 前缀**：同一个 prompt 连发两次，`prompt_eval_duration` 趋近 0，算出 378,831 tok/s 的假数。
    必须每次在开头塞一个唯一 nonce 才能测到真正的 prefill
12. **改 num_ctx 会触发模型重载**：扫 prompt 长度时如果让 num_ctx 跟着变，最长那一点会莫名其妙掉一半。
    先固定上下文长度，再扫 prompt 长度
13. **GitHub 在云端也被断**：gh-proxy 可用但大文件会截断（源码 tarball 反复 TAR_BROKEN）。
    最后走 PyPI 的 `llama-cpp-python` sdist 拿 vendored 源码，76 MB 一次成功
